## 7. Top 5 things to look at first

1. **Host-side git on arm-writable repos (S-1, critical).** `repo.state`, `_diffstat`, `export`, the Task 13
   teammate commit and above all `publish` (`git push` with the owner's credentials, L1885) run host git
   against a `.git/` the arm can rewrite under `bypassPermissions`. `core.fsmonitor`, hooks and
   `credential.helper` in repo-local config execute on the host as the owner. Run git on arm repos in a
   container; push from a clean clone. (It also breaks the speckitty hand edit: beads' git hooks call `bd`.)
2. **What is tested, and whether the arm is told (F-1 / OD4 / Q-4).** The code tests `HEAD`, OD4 says `main`,
   and the "commit on main" instruction only reaches arms that ask. Spec Kit, Spec Kitty and superpowers
   branch by design and would score zero for work sitting on a branch. One identical delivery sentence in
   every handoff; test `refs/heads/main`.
3. **Stop-rule accounting and false halts (C-2, C-3, C-4).** A flaky test caused by the arm's own race is
   classified as a harness fault (and halts on repeat); a harness fault after no-progress attempts doesn't
   reset the attempt count; two transient "overloaded" API errors anywhere halt the bake-off. Classify
   flakiness against the reference, reset counts on restore, retry transient API errors in place.
4. **Model-pin verification can pass without transcripts (C-6), and the dry run can't tell (§3 table).**
   `verify_pin` is `ok` with streams only, the fake writes transcripts exactly where the checker looks, and PO
   transcripts are never checked. Make zero-transcript steps a fault, check stream assistant events, and have
   Task 21 assert the transcript path — then add a one-arm, two-step real canary run (Task 20b) before
   Task 22.
5. **OD6, OD14, OD9 — decisions that change what is measured.** Step 5 as one message probably never tests
   "concurrent" change handling (OpenSpec's sharpest case); 80 exchanges/attempt penalises question-heavy
   methods (BMAD, Spec Kit clarify); marketplace installs plus pass-2 re-setup can put a different plugin
   version into the scored pass. Also check G1/G2: Spec Kitty's tracker binding and beads' `bd setup claude`
   are not in its setup — the "under-cooked setup" failure the owner has seen before.

## 2. Fairness risks

- **F-1 (I) — Branch-by-design methods are penalised by what gets tested.** OD4 tests committed `main`, but the
  code tests `repo.head()` (= `HEAD`, Task 18 L3603 and Task 17 `git_after`), which contradicts OD4. Worse,
  the PO-brief line "Deliver each step committed on `main`" reaches an arm **only if it asks**. Spec Kit's
  `/speckit-specify` creates and checks out an `NNN-*` branch; Spec Kitty uses lanes; superpowers works in a
  worktree and offers merge/PR/keep at the end. They get one nudge per attempt (L2880) and otherwise score
  zero for the step. **Fix:** add one identical delivery sentence to every handoff (harness text, not
  product information), test `refs/heads/main` explicitly, and record the branch state as evidence.
- **F-2 (I) — OD5 "follow the method's recommended next command" favours slash-command methods.** The PO only
  returns `next_command` for text starting with `/` (protocol L2409, `parse` L2540). BMAD names its next
  workflows as skills ("run `bmad-create-architecture`"), and superpowers asks in prose; both fall into
  `continue` and receive "Please continue." instead of the method's own next step. Normalise: accept a named
  installed skill as `next_command` and send it in the method's own invocation form.
- **F-3 (I) — OD19 (one resumed session per attempt) overrides methods that document fresh contexts.** Several
  methods recommend a new chat/`/clear` between phases (BMAD's workflows in particular; Spec Kit's docs
  suggest it between plan and implement). [UNVERIFIED per tool — add to the research/checklist "Known traps".]
  If the method's docs say start fresh, the runner should start a fresh session when the method says so, as
  a user would; otherwise methods designed around context hygiene are run against their docs.
- **F-4 (I) — OD14's 80 exchanges per attempt is not neutral.** BMAD's facilitated PRD/architecture elicitation
  and Spec Kit's `clarify` are question-heavy by design; the control and superpowers' bounded path are not.
  A cap that only question-heavy methods can hit, with `stalled` scored as an arm outcome, penalises a
  documented feature. Raise it well beyond any observed pass-1 count (e.g. 250) and record the count.
- **F-5 (I) — `must_run` lists are author-chosen and uneven.** OpenSpec gets `/opsx:archive` (which merges deltas
  into specs and so directly affects "spec, code and tests agree"), Spec Kit gets `/speckit-converge`, cc-sdd
  `/kiro-validate-impl`, Spec Kitty accept+merge — but superpowers (finishing-a-development-branch), BMAD
  (code review / retrospective) and Spec Kit's `analyze` get nothing. Each `must_run` entry needs a
  CANDIDATES citation in the toml (Review Focus 2 already demands this), and the same rule applied to every
  arm: "the step's documented closing command(s), per the method's docs".
- **F-6 (M) — OD2's alias remap changes some methods more than others.** It is the closest reading of design §11,
  but it silently upgrades superpowers' (and any other method's) deliberately cheaper subagents to Opus. That
  is a change to the method under test and must be reported per arm (the plan says so for superpowers only,
  L2058). A method that names a *full* non-Opus ID in agent frontmatter would fault on every step and halt the
  bake-off — that is an arm-configuration issue, not a harness fault; handle it at setup (see OD2).
- **F-7 (M) — principles are given unevenly** (G3). BMAD receives the principles as a bare setup prompt
  (`"{principles}"`, L1997) with no instruction; OpenSpec receives nothing although it has a documented slot;
  superpowers and control receive nothing (defensible: no slot).
- **F-8 (M) — OD10 (no web tools) removes documented research phases** (Spec Kit's plan writes `research.md`;

  flow tried to research, so Plan 3 does not score it as a weakness.
- **F-9 (M) — OD11 bypassPermissions** is uniform and appropriate *inside* the stage; it only becomes a problem

- **F-10 (M) — OD13 same order in pass 2** carries two biases into the scored pass: the owner's gate behaviour

- **F-11 (M) — The hand edit differs per arm** because an LLM writes it (OD1). Unavoidable, but record the diff

All nine are genuinely resolved by the tester-container design, and Task 15's reference-count docker test
(L3184–3211) is the right acceptance test for them. Two new risks are introduced by the same design:

- **C-1 (I) — mutmut is installed into the arm's `.venv` before the hidden tests run** (Task 15 `prepare`,
  L3117). mutmut 3 pulls `click`, `libcst` and others; `click` is very likely in the arm's own dependencies
  (it's the obvious CLI library). Installing into the same venv can change the arm's resolved versions, so
  the hidden tests would run against an environment the arm never had. Install mutmut into a separate venv
  (or a second copy) after the hidden run.
- **C-2 (I) — arm-caused nondeterminism is classified as a harness fault.** Any test that fails then passes on
  re-run is `flaky` → `flaky-test` harness fault (L3132, L3438, L3605–3613). A race in the *arm's* watcher
  (step 2 is exactly where arms will have races) becomes "the owner fixes the test", and its second
  occurrence halts the whole bake-off. Before classifying, re-run the same test 3× against the reference
  (already in the image for the dry run); flaky on the reference = harness fault, stable on the reference =
  arm result (`flaky-arm`, counted as failed, with the flake recorded).

### Stop rules and attempt accounting (Task 18)

- **C-3 (I) — a harness fault after a no-progress attempt does not reset the attempt count.** In `run_step`
  (L3593–3601) a `HarnessFault` restores the step snapshot and restarts from `first_message`, but
  `arm_attempts`, `ar_history` and `attempt` are not reset, and the earlier no-progress attempts' turns and
  questions stay at the top level (only harness-labelled attempts are parked). The restored arm then gets
  fewer than three attempts, and the evidence mixes a discarded timeline with the re-run. Reset all three and
  park the discarded no-progress attempts under the harness label.
- **C-4 (I) — transient API errors will halt the bake-off.** `infra-api` signatures strip digits
  (L2840), so two "API Error: overloaded" anywhere between owner resolutions halt everything (design §9
  literally). Over a multi-week run that is near-certain. Retry transient classes (5xx/overloaded/rate
  limit) in place, resuming the same session with backoff, before recording a harness fault; and don't throw
  away a 4-hour attempt (full step restore) for a 529.
- **C-5 (M) — PO infrastructure failures are mislabelled `po-protocol:unparseable`.** `po.decide` raises
  `ProtocolError` for any non-`ok` PO outcome (L2583–2584), and `drive` maps every `ProtocolError` to the same
  signature (L2850), so an auth blip and a genuinely bad reply count as "the same fault twice".
- **C-6 (I) — the model-pin check can pass without looking at a single transcript.** `verify_pin` returns
  `ok` when there are stream files but no transcript files (L3695), and stream checking covers only `init`
  and `result.modelUsage`, not assistant events. If the transcript path assumption (`projects/<slug>/`) is
  wrong — which only the live probe can tell, because the fake writes exactly where the plan assumes
  (L1350) — every step passes the pin check on streams alone. Make "zero transcript files for an arm step" a
  `model-pin:no-evidence` fault (as the note at L1698 already claims), check stream `assistant` events too,
  and collect + verify PO transcripts (PO home, L2570) as well. Also handle a truncated last JSONL line
  (a timed-out turn) instead of crashing in `json.loads` (L1683).
- **C-7 (M) — the no-progress nudge is hidden-test feedback.** "Acceptance testing found that none of this
  step's new behaviour works yet" (L2328) tells the arm something only the hidden tests know. It is identical
  and counts-only, so it is fair, but it is a spec change to design §9 (see OD3).
- **C-8 (M) — owner gate visibility depends on PO classification.** A missed `approval` (classified as
  `continue`) never reaches the owner. List every `continue` decision whose arm message contains
  approve/sign-off/proceed wording in `summary.md`, so the owner can spot misses.

### Container, signal, env and path handling

- **C-9 (I) — stderr is piped and never read** (`_run`, L1487–1489). Claude Code writing more than the pipe
  buffer to stderr blocks the container until the 4-hour timeout, which is then scored as an arm `timeout`.
  Drain stderr concurrently and save it as `turns/NNN.stderr.gz`.
- **C-10 (I) — `mentioned_in_session` over-counts** (Task 13 `detect`, L3028). Counting `TROUPE_THEATRE` in
  streams and transcripts includes tool *results*: an arm that merely `Read`s `cli.py` "mentions" it. Count
  assistant text and tool *inputs* only. (Owner's rule on overclaiming applies to facts as well as tests.)
- **C-11 (I) — the hand-edit scope check will fail on ordinary side effects.** The teammate is not told not to run
  things; `uv run` can rewrite `uv.lock`, and running tests creates `__pycache__/*.pyc` and `.pytest_cache`,
  which `git status --porcelain -uall` lists (L3018) and `scope_ok` rejects. Two failures raise a harness
  fault; the same fault at another arm halts the bake-off. Revert non-`.py` changes automatically (record
  them) and only fail on a *tracked* non-`.py` edit.
- **C-12 (I) — the teammate prompt may leak to the arm via `/inbox`.** Every `Turn` carries an `inbox` and
  the PO uses the *arm's* inbox (L2581); if `handedit.apply` does the same, `/inbox/teammate-…md` ("Make
  `troupe config` use TROUPE_THEATRE…") is readable by the arm at step 2, defeating "unannounced". Give each
  role its own inbox and mount only the current message file into arm containers.
- **C-13 (M) — `docker.sweep()` removes containers but not networks** (L1062–1067). After a crash,
  `bk-net-<pass>-<arm>-<phase>` still exists and `Stage.__enter__` fails with "already exists" → an
  `infra-container` fault. Sweep labelled networks too.
- **C-14 (M) — the dummy-credential guard is never called.** `Credential.check_allowed` (L1213) is tested
  (L1192) but no call site in `session`, `drive`, `po` or `orchestrate` invokes it. The same applies in
  reverse: nothing stops the real keychain credential from driving a dry arm.
- **C-15 (M) — `ARM_VERSION_PROBES["ccsdd"]` records `npm ls -g`'s first line** (the prefix path), not the
  version (L767, L760).
- **C-16 (M) — `init.claude_code_version` is recorded but never compared to the pin per turn.** It's a cheap,
  exact check on the one pin that matters most after the model.

## 4. Security

- **S-1 (C) — host-side git on arm-controlled repos breaks the sandbox.** The arm runs with
  `bypassPermissions` and read-write access to its `work/` (L2824), which contains `.git/config` and
  `.git/hooks`. The runner then runs **host** git on that repo: `git status` (`repo.state`, L1838),
  `git diff --stat` (L2815), `git archive` (L1858), `git grep` (Task 13), `git commit` (Task 13's teammate
  commit, "git add -A && git commit", L3018 — location unspecified), and **`git push origin main` with the
  owner's own GitHub credentials** (`publish`, L1885). Repo-local config can execute arbitrary host commands
  as the owner: `core.fsmonitor` (runs on `status`/`diff`), `diff.<drv>.textconv`/`diff.external`,
  filter drivers via `.gitattributes`, hooks (`pre-commit`, `pre-push`), and `credential.helper` /
  `core.sshCommand` on push — the last one can capture the owner's GitHub credential. No malice is required
  for breakage either: beads installs git hooks (`bd init`) that call `bd`, which does not exist on the host,
  so a host-side teammate commit in the speckitty arm fails. **Fix:** run every git command that touches an
  arm repo **inside a container** (the arm image, network none); for the push, push from a clean
  `git clone --no-local` / bundle of `main` into a scratch directory the arm never touched, or push from a
  container holding a repo-scoped token. At minimum, host git must use
